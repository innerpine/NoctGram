# Почтовый вход Noctgram

Подготовлены `/login`, `/welcome` и серверные `/api/auth/*`. Реальные письма появляются после подключения Supabase Auth и почтового сервиса. Пока почтовые настройки пусты, вход сообщает, что отправка не подключена. Старый вход через ChatGPT доступен только при явном `NOCT_AUTH_MODE=hybrid` за доверенным Sites-шлюзом или локально. Пустой или неизвестный режим не включает этот fallback. Тестовых кодов и обхода подтверждения в приложении нет.

## 1. Настройте Supabase и письма

1. Создайте проект Supabase. Данные Noctgram остаются в D1/R2; в Supabase хранится только почтовая идентификация.
2. В Auth включите Email и разрешите регистрацию. Подтверждение почты должно оставаться включённым.
3. Настройте **Email OTP expiration = 300 секунд**, **длину кода = 6 цифр** и интервал повторной отправки не меньше 60 секунд. Код дополнительно ограничен 5 минутами в Noctgram.
4. В шаблонах **Magic Link** и **Confirm signup** используйте `{{ .Token }}`: готовый HTML находится в `email-templates/login-code.html`. Укажите тему «Код входа в Noctgram». Нужен код для ввода, а не ссылка.
5. Подключите Custom SMTP: например, Resend или другой совместимый сервис. Подтвердите домен отправителя и настройте SPF, DKIM, DMARC по инструкции провайдера. Встроенная тестовая почта Supabase не предназначена для публичного запуска.
6. В Auth URL Configuration укажите окончательный адрес Noctgram. Проверьте доставку на используемые аудиторией почтовые сервисы.

Ссылки: [Email OTP](https://supabase.com/docs/guides/auth/auth-email-passwordless), [Custom SMTP](https://supabase.com/docs/guides/auth/auth-smtp), [лимиты](https://supabase.com/docs/guides/auth/rate-limits).

## 2. Подключите приложение

В локальном `.env` заполните:

```dotenv
NOCT_AUTH_MODE=hybrid
SUPABASE_URL=https://PROJECT_REF.supabase.co
SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
```

Нужен именно publishable key (допустим прежний anon key), **не service_role и не secret/admin key**. Ключ SMTP задаётся только в Supabase, не в клиентском коде Noctgram. После изменения `.env` перезапустите локальный сервер. При размещении задайте те же переменные в серверном окружении хостинга — локальный `.env` туда не копируется. `.openai/hosting.json` не предназначен для ключей.

Используется HTTP API Supabase, без отдельной клиентской библиотеки. OTP проверяется сервером через `/auth/v1/verify`; `user.id` и подтверждённая почта принимаются только из ответа провайдера. Токены Supabase не возвращаются браузеру и не сохраняются в D1.

## 3. Сохраните существующий профиль

1. Оставьте `NOCT_AUTH_MODE=hybrid` на время перехода.
2. Войдите прежним способом, откройте **Профиль → Редактировать → Почта для входа**.
3. Введите почту и подтвердите код. Привязка сохраняет ID профиля, посты, каналы, Stars и роль модератора.
4. Проверьте вход по этой почте в отдельном браузере, прежде чем отключать прежний способ.

Привязка требует действующей сессии исходного аккаунта и кода из письма. Автоматического объединения по юзернейму, отображаемому имени или email из заголовка нет. Один аккаунт может иметь одну почтовую идентификацию; почта, уже привязанная к другому профилю, не переносится автоматически. Смена привязанной почты — отдельная будущая функция.

**Локальный и размещённый аккаунты не являются одной базой.** Привязка локального Seedy сохраняет локальные данные. Перед публикацией отдельно определите миграцию данных и выдачу роли на рабочем ID; не назначайте администратора по выбранному юзернейму.

## 4. Выберите окружение запуска

Сейчас Site зарегистрирован приватным и ещё не опубликован. Закрытый доступ Sites требует входа платформы перед загрузкой самого сайта. Почтовый вход внутри приложения не отменяет эту внешнюю проверку.

Для самостоятельного публичного входа нужны публичный доступ на уровне размещения либо самостоятельный хостинг. Доступ сайта этой задачей не меняется.

- `hybrid` — почта и старый вход Sites. Этот режим допустим только за доверенным диспетчером Sites, который управляет заголовками `oai-authenticated-*`, либо в локальном тестовом окружении.
- `email` — только почта; приложение полностью игнорирует `oai-authenticated-*`. Используйте этот режим при самостоятельном размещении и после проверенного перехода существующих аккаунтов.

Окончательный сервер должен работать через HTTPS: cookie сессии получит `Secure`, `HttpOnly`, `SameSite=Lax`. В D1 хранится только SHA-256 случайного 256-битного секрета сессии. Срок входа — 30 дней; выход удаляет сессию на сервере. Блокировки и read-only продолжают проверяться на каждом действии в Noctgram.

## Первый вход

После подтверждения почты новый пользователь выбирает обязательные имя и юзернейм, а также необязательную аватарку до 5 МБ (JPG, PNG, WebP, GIF). Без аватарки показываются инициалы. Невозможно публиковать и использовать социальные API до сохранения профиля. Конфликт юзернейма откатывает всё сохранение; можно выбрать другое имя без потери введённых данных. Незавершённые профили скрыты из общих списков.

## Проверки перед включением реальных писем

- Примените новую миграцию `drizzle/0004_regular_stardust.sql` один раз после предыдущих. В текущих локальной и изолированной тестовой базах она уже применена. Старые пользователи получают `onboardingComplete=1`; только новые почтовые аккаунты проходят настройку.
- Проверьте реальное письмо, неверный/истёкший/повторно использованный код, повторный вход, выход и привязку своего профиля.
- Настройте квоты Supabase и SMTP. Noctgram дополнительно ограничивает отправку и проверку по почте/IP и по сессии ввода. При проксировании IP должен поступать из доверенного источника; без него используется общий лимит.
- Доступ к API провайдера может быть вызван напрямую с publishable key, поэтому лимиты Supabase обязательны. Если включаете CAPTCHA Supabase, сначала добавьте виджет и передачу CAPTCHA-токена; текущий интерфейс этого не делает.
- Восстановление потерянной почты, смена почты, список устройств и выход со всех устройств в эту задачу не входят. Для администратора перед публичным запуском нужна отдельная дополнительная защита входа.

## Локальные тесты без отправки писем

`tests/auth.integration.mjs` поднимает подменный HTTP-провайдер на `127.0.0.1:8791` и проверяет production Worker на `8787`. Используйте только изолированную базу со всеми миграциями и `tests/fixtures/moderation.sql`. Перед каждым запуском применяйте также `tests/fixtures/auth.sql`: она сбрасывает почтовую привязку только фикстурного модератора и добавляет истёкшие сессии для проверки:

```powershell
npm run build
npx wrangler d1 execute DB --local --config wrangler.local.json --persist-to work/auth-qa --file tests/fixtures/auth.sql
npx wrangler dev --config dist/server/wrangler.json --port 8787 --persist-to work/auth-qa --var NOCT_AUTH_MODE:hybrid --var SUPABASE_URL:http://127.0.0.1:8791 --var SUPABASE_PUBLISHABLE_KEY:qa-publishable --var NOCT_AUTH_ALLOW_LOCAL_PROVIDER:1
```

В другом терминале: `node tests/auth.integration.mjs`. Фикстуры и параметры провайдера предназначены только для тестового Worker. **Не задавайте `NOCT_AUTH_ALLOW_LOCAL_PROVIDER` в рабочем окружении.** Провайдер находится только в тестовом файле; в сборке приложения нет выдачи тестовых кодов.

Отдельная проверка: перезапустите этот Worker с `--var NOCT_AUTH_MODE:email`, убрав три тестовые переменные Supabase/локального провайдера, и выполните `node tests/auth-email-only.integration.mjs`. Она проверяет отказ поддельным заголовкам Sites и отсутствие ложной отправки при пустых настройках.

Сессиями приложения управляет Noctgram в D1. Удаление пользователя только в консоли Supabase не отзывает уже выданные сессии Noctgram: для немедленного прекращения доступа используйте блокировку в Noctgram. При будущем удалении аккаунта нужно также удалить все его записи `auth_sessions`.

# Подключение музыкальных аккаунтов

Страница: `/music/services` или «Музыка → Подключить музыкальные сервисы». Она повторяет сценарий из предоставленного примера Dotify: выбор сервиса, вход, проверяемый статус аккаунта, личные плейлисты и импорт. Используется существующая авторизация Noctgram; музыкальный аккаунт привязывается к уже вошедшему пользователю.

## Готовые адаптеры

| Сервис | Вход | Личные плейлисты | Поиск | Прослушивание |
| --- | --- | --- | --- | --- |
| SoundCloud | OAuth с PKCE и серверным секретом | Получение списка с догрузкой, сохранение в личной коллекции | Треки | Публичные ссылки через официальный виджет, приватные — в SoundCloud |
| Spotify | OAuth с PKCE | Получение списка с догрузкой, сохранение метаданных в личной коллекции | Не добавлен | Переход в Spotify |
| Яндекс Музыка, YouTube, VK Музыка, Deezer | Адаптеры не реализованы | Недоступно | Недоступно | Недоступно внутри Noctgram |

OAuth-импорт сохраняет ссылку, название, обложку и число треков выбранного плейлиста в личной коллекции. Аудио и состав плейлиста остаются у сервиса. Это не скачивание аудио и не локальная копия каждого трека. Импортированные данные не попадают в общие открытия, музыкальные чарты или профили других пользователей. OAuth-адаптер Spotify используется для переноса метаданных пользовательских плейлистов. См. [Spotify Developer Policy](https://developer.spotify.com/policy), раздел III.

Отдельно в `/music` можно добавить публичную ссылку на трек Spotify и прикрепить собственный аудиофайл. Этот сценарий не требует музыкального аккаунта, Premium или OAuth: сведения берутся из публичных метаданных, а воспроизводится личный файл из R2. Подробнее: [MUSIC.md](MUSIC.md).

## Однократная настройка владельцем

`Client ID` идентифицирует приложение Noctgram. Он не подтверждает вход пользователя. Каждый пользователь входит на официальной странице сервиса и разрешает доступ своему аккаунту; пароль и токены не вводятся в интерфейс Noctgram.

1. Применить **новую** миграцию `drizzle/0008_polite_adam_destine.sql` к базе, где уже выполнены 0000–0007. Для пустой базы выполнить все миграции по порядку. Повторно старые миграции не выполнять.
2. Заполнить переменные в личном `.env` по `.env.example`. Для размещённого проекта задать их как runtime secrets. `.env` и ключи не добавлять в Git.
3. Зарегистрировать точные callback URL в кабинетах музыкальных сервисов. Открывать приложение на том же origin, который указан в callback. Код проверяет совпадение и не использует произвольный Host для перенаправления.
4. Перезапустить локальный сервер, открыть `/music/services` и нажать «Подключить». Кнопка станет доступна, когда сервер увидит все необходимые настройки.

### Шифрование

`MUSIC_TOKEN_KEY` — отдельные 32 случайных байта в виде 64 шестнадцатеричных символов. В текущей локальной `.env` ключ уже создан. На другом компьютере с новой базой нужен собственный ключ. Существующую базу подключений необходимо переносить вместе с её ключом через защищённое хранилище; замена ключа потребует повторного подключения аккаунтов.

Токены доступа, обновления и PKCE-verifier шифруются AES-256-GCM с привязкой к пользователю, сервису и назначению. OAuth state связан с текущей сессией Noctgram и HttpOnly-cookie браузера, действует 10 минут, используется один раз. В ответах API, URL плеера и localStorage токенов нет.

### SoundCloud

Регистрация приложения и актуальные требования описаны в [официальном API Guide](https://developers.soundcloud.com/docs/api/guide#authentication). На момент реализации SoundCloud указывает Artist Pro как условие получения API-ключей.

```dotenv
SOUNDCLOUD_CLIENT_ID=
SOUNDCLOUD_CLIENT_SECRET=
SOUNDCLOUD_REDIRECT_URI=http://localhost:3000/api/music/services/soundcloud/callback
```

В размещённом приложении вместо `http://localhost:3000` нужен точный HTTPS-origin Noctgram. Все запросы обмена кода и обновления токена идут с сервера на `secure.soundcloud.com`; данные аккаунта запрашиваются с `api.soundcloud.com`. Обновления выполняются под блокировкой в D1: одноразовый refresh token не расходуется одновременно несколькими вкладками. Если исход обновления неизвестен, требуется повторный вход.

### Spotify

Создать приложение в [Spotify Developer Dashboard](https://developer.spotify.com/dashboard) и зарегистрировать callback. Используется [Authorization Code with PKCE](https://developer.spotify.com/documentation/web-api/tutorials/code-pkce-flow) с разрешениями `playlist-read-private playlist-read-collaborative`. Секрет клиента для выбранного PKCE-потока не используется.

```dotenv
SPOTIFY_CLIENT_ID=
SPOTIFY_REDIRECT_URI=http://127.0.0.1:3000/api/music/services/spotify/callback
```

Для Spotify локально открыть Noctgram через `http://127.0.0.1:3000`, войти в Noctgram на этом адресе и затем подключить Spotify. `localhost` не подходит по [правилам redirect URI Spotify](https://developer.spotify.com/documentation/web-api/concepts/redirect_uri). Публичное приложение использует HTTPS. Доступ реальных пользователей также зависит от режима приложения и разрешений Spotify; конфигурация клиента сама по себе не отменяет эти ограничения.

## Отключение и пределы

«Отключить» удаляет сохранённые в Noctgram токены, незавершённые попытки входа и импортированные плейлисты выбранного сервиса. Запоздавшие callback и обновления токена не восстанавливают отключённый аккаунт. Read-only может удалить подключение. Выданное разрешение на стороне провайдера при необходимости также отзывается в настройках самого SoundCloud/Spotify; отдельного удалённого отзыва из Noctgram пока нет.

Названия новых сервисов в переключателе — явные недоступные состояния, а не работающие интеграции. Переключатель локального/удалённого выполнения из Dotify не добавлен: здесь запросы аккаунта выполняет сервер Noctgram. Ручной ввод чужих client IDs и пользовательских токенов не реализован.

## Проверки

```powershell
npx tsc --noEmit
npm run lint
npm run build
node tests/music-services.test.mjs
```

Тест выполняет настоящий код адаптеров и SQL миграций в изолированной SQLite-базе. Ответы SoundCloud/Spotify заменены тестовыми, реальные аккаунты и сеть не используются. Проверяются PKCE по стандартному вектору, шифрование, подмена владельца/cookie, повторное использование state, скрытие секретов, личные импорты, защищённая пагинация, одновременное обновление токенов и отключение во время OAuth/refresh.

Реальный OAuth-вход, доступность конкретных плейлистов и браузерное воспроизведение требуют проверки после настройки зарегистрированных приложений. Успешные автоматические тесты не означают, что реальные аккаунты уже подключены.

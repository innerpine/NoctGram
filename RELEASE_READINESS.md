# Проверка перед самостоятельным размещением

Локальные проверки не подтверждают настройки работающего облака. Эти команды ничего не публикуют, не создают ресурсы и не изменяют D1/R2. Тестовая экономика Premium/Stars отключена; реальная оплата и возвраты описаны в [COMMERCE.md](COMMERCE.md). Автоматические проверки используют искусственные платежи и не подтверждают реальное списание.

## Проверки исходников

На Node.js 22.13 или новее:

```text
npm ci
npm run typecheck
npm run lint
npm test
npm run build
npm run check:secrets
npm audit --audit-level=high
```

GitHub Actions повторяет проверку типов, lint, последовательные тесты и сборку на Windows и Linux; проверка зависимостей выполняется на Linux. У workflow только разрешение чтения исходников, без секретов приложения и без публикации. Ошибка любого шага блокирует успешный результат CI; в настройках репозитория проверку нужно отдельно сделать обязательной для слияния. Умеренные advisories тоже требуют рассмотрения; порог автоматического отказа — high/critical. Не добавлять blanket-исключения для прохождения проверки.

`npm test` перечисляет только `tests/*.test.mjs` и запускает Node с `--test-concurrency=1`. `node scripts/run-tests.mjs --list` показывает состав. Скрипты `*.integration.mjs` требуют отдельно подготовленного изолированного Worker и этим запуском не выполняются. Не направлять их на рабочую базу.

`check:secrets` проверяет текущие отслеживаемые Git текстовые файлы по известным форматам токенов, а также запрещённые имена файлов. Локальные неотслеживаемые `.env` не читаются; совпавшие значения и строки исходника не выводятся. Это ограниченная проверка, которая не заменяет анализ истории Git, энтропии, журналов CI, облачных секретов и собранных клиентских файлов. Ошибка Git или слишком большой файл приводит к отказу проверки, а не тихому успеху. Бинарные файлы и symlink-содержимое не сканируются.

## Явный режим standalone

Обычные `npm run dev` и `npm run build` сохраняют существующий процесс Sites/локальной разработки. `hybrid` подходит только для локального окружения или доверенного Sites-шлюза, который сам управляет identity-заголовками. Ни `hybrid`, ни неизвестный/пустой режим не подходят для открытого standalone Worker.

Для открытого standalone окружения требуются `NOCT_AUTH_MODE=email` и `NOCT_DEPLOYMENT_TARGET=standalone`. Последний включает отказ в авторизации при случайном переключении публичного Worker в hybrid. Для закрытого preview используется `NOCT_AUTH_MODE=access`, точный audience, домен команды и список участников из [SHARED_PREVIEW.md](SHARED_PREVIEW.md). Валидатор отдельный: его не нужно добавлять к обычной сборке Sites. Текущий `NOCT_PREVIEW_CONFIG` предназначен для Access preview; успешная проверка JSON с `email` сама по себе не создаёт отдельную публичную сборку. Для публичного выпуска нужен явно подготовленный standalone путь сборки и проверка его итогового конфига.

Проверяйте именно итоговый Wrangler JSON для выбранного окружения, со всеми разрешёнными переменными и привязками. Валидатор принимает JSON без комментариев, отказывается от вложенных `env` и не читает `.env` или переменные процесса. Не используйте локальные placeholder-привязки. Если используется `wrangler --env`, сначала подготовьте итоговый конфиг для этого окружения: проверка другого файла не покрывает поздние overrides.

```text
npm run check:deployment -- --config work/standalone-resolved.json --target public --secret-names work/standalone-secret-names.json
npm run check:deployment -- --config dist/server/wrangler.json --target access-preview --secret-names work/preview-secret-names.json
```

Инвентарь содержит **только имена**, например `["SUPABASE_PUBLISHABLE_KEY", "NOCT_JOBS_SECRET"]`. Допускается также JSON-массив объектов `{ "name": "NOCT_JOBS_SECRET", "type": "secret_text" }`, полученный read-only командой `wrangler secret list` для точного Worker/окружения. Хранить оба файла в игнорируемом `work/`. Сам валидатор не обращается к Cloudflare и не выводит конфиг, адреса участников, IDs ресурсов или значения ключей. Инвентарь подтверждает только наличие имени, а не правильность или непустоту действующего секрета.

Проверяются `DB` и `FILES`, явный режим входа, необходимые параметры почты или Access, отключение локального почтового провайдера, зависимости включённых OAuth/TURN/push и секрет заданий при cron. Секреты подписи, TURN, бота и OAuth должны храниться в Worker secrets. Для отключённых интеграций ключи не требуются. Если фоновые задания выполняет отдельный Worker, отдельно проверьте общий `NOCT_JOBS_SECRET`, HTTPS origin и активный планировщик по [REALTIME_SETUP.md](REALTIME_SETUP.md).

## Проверка реального окружения владельцем

1. Сверить Worker, аккаунт, D1 и закрытый R2 с конкретным выпуском. Проверить миграции на копии данных и восстановление D1/R2 до изменения рабочей схемы. Успех валидатора не подтверждает существование ресурсов.
2. Проверить все адреса доступа, включая `workers.dev`, preview URL и основной домен. Для Access каждый адрес должен требовать проверенный JWT; публичный email Worker должен отвергать подставленные `oai-authenticated-*` заголовки. Не публиковать Vite dev-сервер и не считать защиту основного домена защитой прямого адреса Worker.
3. Подтвердить доставку почтового кода новому адресу, вход/выход и отключение отозванной сессии. Для Access проверить разрешённого и постороннего участника. Секреты не помещать в URL, исходники или журнал проверки.
4. Проверить доставку уведомлений и фоновые задания, звонки между разными сетями с TURN, серверные лимиты поиска и загрузок, бюджет закрытого preview и сообщение о постоянном исчерпании. Определить оповещения об ошибках, расходах и переполнении очереди.
5. После изменения настроек и миграций повторить проверку итогового конфига и smoke-проверки. Зафиксировать commit, результаты CI, миграции, резервную копию и способ отката. Публикация, изменение облачных ресурсов и восстановление данных выполняются отдельным согласованным процессом владельца.
